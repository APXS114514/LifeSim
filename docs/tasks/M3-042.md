## 目标

把「每年 0.24 条可见事件」提高到 P1 目标的密度（[V0.1_PLAN](../V0.1_PLAN.md) §2：均值 ≥ 1.5 条/年、≥ 90% 的年份至少 1 条）：
建立**一个**数据驱动的原型目录（20 个通用人生事件）与**一个**公共年度运行器，覆盖童年、学校、青年、成年、老年的日常
（友谊、兴趣、小意外、邻里、压力与休息、学会新技能、同学重聚、退休后的生活），后果落到细状态、关系与金钱。

本任务同时交付：集中登记的概率表（D 级设计假设）与逐原型的资格/后果/双语模板、频率预算的算法与数值、
供界面「这是什么」使用的披露数据，以及逐原型的可执行验收测试。

## 背景（执行者必须知道的事实与已定的决定）

### 1. 现状基线（M5-001 的度量口径）

[M5-001](M5-001.md) 的细化稿里有一份 2026-10-21 的实测基线（五国各 100 局，本机 Apple M5、Node v24.21.0）：

| 指标                                    | 数值                                                    |
| --------------------------------------- | ------------------------------------------------------- |
| 每局事实                                | 83.6 条（其中约 76% 是 `finance.settlement`，默认隐藏） |
| 可见事实 / 在世年（pooled，五国）       | **0.2398**（逐国 0.2044—0.3209）                        |
| 无事件年份比例（pooled）                | **0.8596**（逐国 0.8220—0.8765）                        |
| 每局可选决定（`all` 口径）均值 / 中位数 | 1.26 / 1                                                |
| 每局耗时 p50                            | 6.0—8.2 ms（M5-001 的 10,000 局实测）                   |

口径定义（与 M5-001 一致，**本任务沿用，不得另立**）：

- **可见事实** = 除 `finance.settlement` 之外的全部事实（含 `decision.made`、含父母的 `npc.*`）。
- **在世年份** = 出生年…死亡年（含两端）的自然年数。
- **每年可见事件数** = Σ可见事实 / Σ在世年份（pooled）；**无事件年份比例** = 没有任何可见事实的在世年份数 / Σ在世年份数。

M3-011 已合并，父母的 `npc.*` 事实已经在时间线上；把它们计入「可见事件」是**正确**口径（V0.1_PLAN 的体验目标是
「玩家每年能看到什么」，不是「主角自己有多少条事实」）。本任务的估算把这条基线当作**加数**，而不是减数。

### 2. 现有事件与随机流的机制（本任务必须复用的部分）

- 事件是 `EventDefinition`（`packages/simulation-core/src/types.ts`）：`type`、`version`、`priority`、可选的
  `decision`、`handle(ctx)`。**幂等键 = `occurrenceKey(type, entityId, period)` = `type|entityId|period`**，
  随机流是 `deriveStream(rootSeed, key)`（`simulation-core/src/random.ts`）；`ctx.random.chance(p)` **恰好消耗一次抽样**，
  与 p 的取值无关。
- 一天内的处理全序 = 日期 → 优先级 → 幂等键（`scheduler.ts` 的 `compareOccurrences`）。因此同一天里多个原型事实的
  叙事顺序由**类型名**决定，与目录数组顺序无关（可测试、可复现）。
- 引擎对**每个事件**做一次状态草稿克隆，事实与不变量整体提交（`engine.ts:#processHead`）。**事件数是每局成本的主要变量**，
  本任务会新增约 500 个事件/局；这是已知且被 V0.1_PLAN §8 预期的代价（见「实现要求 10」）。
- 引擎硬上限：`maxEventsPerDay` 500、`maxChainDepth` 64、`maxSchedulesPerEvent` 64。原型每天最多 8 个事件、生日当天
  最多新增 8 条排程，远低于上限。
- 决策事件在 `handle` **之前**先跑 `decision.options()` 并写入 `decision.made`（`engine.ts:#resolveChoice`）。
  所以「今年会不会发生」的抽样**不能**放进决策事件：否则玩家会在事件没发生的年份被提问（见「实现要求 4」的两段式）。
- 事实结构 `SimEventFact`：`type`、`templateId`、`outcomeCode`、`details`（camelCase、标量）、`evidenceIds`；
  叙事渲染 `templates.<templateId>` 与 `enums.<参数名>.<值>`（`packages/narrative/src/index.ts`：
  `createTemplateNarrator` / `flattenMessages` / `checkLocaleParity`）。`templateId` 用点号访问嵌套树。
- 主角的年度排程点是 `life.birthday`（`systems/src/life.ts`），NPC 的是 `npc.birthday`（`systems/src/npc.ts`）。
  **本任务的 20 个原型只给主角排程**：父母的人生进程已由 M3-011 的 NPC 事件承担，不再叠加。
- `shared.ts` 的 `PRIORITY` 定义一天内的先后（birthday 10、settle 20、education 30、career 40、health 50、treatment 55）。
  原型事件排在 **60**（见「实现要求 2」）。

### 3. 细状态：ADR-0010 B 尚未补完

[ADR-0010](../adr/0010-character-identity-and-fine-state.md) A 部分（`sex`、`name`、分性别死亡率）已采纳；
**B 部分（细状态）是提议**，明确写着「等 M3-042 细化确定事件需要什么之后补进本节」。
本任务在「所需细状态字段」一节给出**需求与候选**（字段名、取值范围、谁能改、如何派生为 M4-016 指标），
但**不修改契约、不替维护者决定**；实施时以 ADR-0010 B 的最终采纳文本为准（见「可能的阻塞」1）。

现状（`content-schema/src/character-state.ts`）：`origin`（城乡、家境）、`traits.aptitude`、`education`、`employment`、
`health.conditions`（慢性病）、`finance`（指向 `householdAccounts` 的余额）、`lifePrinciples`；
关系（`content-schema/src/relationships.ts`）带 `bonds: { trust, intimacy, conflict } ∈ [0,1]`。
**没有**压力、社交联系、技能/兴趣，也没有任何「近期经历」的存储。

### 4. 「概率是 D 级设计假设」的既有约定

- 概率是**设计假设**（D 级），不是统计结论；GDD §9.1 与 [DATA_POLICY](../DATA_POLICY.md) 要求披露。
  本任务把 20 个原型的所有概率集中在一张表（本文「原型目录」）并在代码里导出披露数据（「实现要求 8」）。
- 原型事实**不引用任何数据表**（`evidenceIds: []`）：它们的依据是设计假设，而不是 WPP/WDI 之类的序列；
  引用 `region.evidence` 会谎称有数据来源（见「验收测试 21」）。

### 5. 已定的约束（骨架原文，一字未改）

1. **目录结构**：每个原型是一条数据（资格条件、年度概率、后果、可选的非重大选择、叙事模板键），由一个公共运行器统一调度与结算；不得为每个事件手写一套调度。该目录就是 M3-023 所说的「事件目录框架」，M3-023 在此之上加中国大陆特色事件。
2. **资格**：年龄区间、年代窗口（不得出现时代错位，例如 1950 年代的智能手机）、城乡、就学/就业状态；涉及国家或年代差异时写明依据，没有依据就保守地不开放。
3. **概率是 D 级设计假设**：集中登记在一张表里并在界面「这是什么」中披露；不得写成统计结论，不得引用不支持它的数据表作为证据。
4. **后果必须落到状态**（M3-043 的细状态、关系、健康、金钱），从而影响派生指标与后续事件；不得只写一句叙事。
5. 每个原型都有资格测试与中英模板；不出现真实人名；暴力、自杀、战争等严肃内容不在 v1（受 Q10 约束）。
6. **随机流**：每个原型的抽样使用以（原型 ID、实体、年份）为键的独立事件，新增原型不改变已有事件的随机数。

**解读（不改变约束，只把实现口径写死）**：

- 约束 1 的「一条数据」落成 `LifeEventPrototype` 对象（纯数据 + 纯函数），运行器只有**一个**工厂函数与**一条**年度排程链。
- 约束 2 的「没有依据就保守地不开放」落成：需要逐国核实的电子产品事件（电视、电话、手机、互联网）**v1 一律不做**，
  留给 M3-023—027（它们能逐国给依据）；本任务只在**年代**上开窗（例如书信 2005 年截止，理由见该原型）。
- 约束 4 落成「每个原型至少写一个状态字段」的硬要求（测试 12）。
- 约束 6 落成：事件 `type = life.<原型 ID>`、`period = year:<YYYY>`，因此**幂等键与随机流键都含原型 ID、实体与年份**；
  每个原型的第一个抽样必须是「今年是否发生」的那一次 `chance(p)`（测试 10 会独立重算并比对）。

## 逐原型规格

约定（20 个原型都适用，逐条在测试里覆盖）：

- **资格**：`age ∈ [from, to]` **且** `year ∈ era`；覆盖型原型只看这两条，非覆盖型另加 `eligible` 谓词（第 20 个）。
- **抽样顺序（硬要求）**：① `chance(annualProbability)` → ② 变体 `weighted`（只有 1 个可用变体时**不消耗**抽样）
  → ③ 决策事件（若有）。变体与决策的后果**禁止**再抽随机数。
- **后果写入**：可加 clamp 到 [0,1]；同一原型同一年最多一个变体。
- 模板键 = `life.<原型 ID>.<变体 ID>`；决策事实（`decision.made`）的模板键 = `life.<原型 ID>.choice.<选项 ID>`。
- 叙事**不用人名、不用性别代词**：中文不用「他/她/他们/她们」，英文不用 `he/she/him/her/his/hers`；
  需要指人时用关系称谓（家人、父母、邻居、同学、朋友、老师、同龄人）。英文一律用无主语的过去式。
- 每个原型的 `details` 只放模板真正用到的参数（`costMinor`、`currency`、`hobby`、`skill`）。

### 1 `early-childhood`：幼儿时光（1—6 岁，p 0.65，上限 6）

- **资格**：年龄 1—6；年代 1950—∞。覆盖型。
- **读**：无（三个变体的措辞不区分城乡）；也不读健康——幼儿的「小病」不建状态（见「所需细状态字段」1）。
- **写**：`stress −0.04`（三个变体都是）、`bonds.intimacy +0.03`（亲代两个方向里主角这一侧，见「实现要求 6」）。
- **变体**：`at-home`（在家）、`errand`（跟着出门）、`sick-day`（病了一场）。
- **边界**：0 岁不发生（下限 1）；7 岁不发生（上限 6）。

```text
at-home   zh: 在家的日子：吃饭、睡觉，家里人多照看着。      en: Days at home: meals, naps, and family keeping watch.
errand    zh: 跟着家里人出门办事，走了很远的路。            en: Went out on errands with family and walked a long way.
sick-day  zh: 发了一场小病，家里人轮流照看。                en: A short illness; family took turns keeping watch.
```

## 所需细状态字段

**这一节是需求与候选，不是已定契约。** ADR-0010 B 由 Claude Code 与维护者补完；本任务只说明 20 个原型真正需要什么、
为什么需要、有什么可接受的替代方案。若 B 的最终文本与本节的字段名不同，以 B 为准（实施时改代码，不改本节的历史记录）。

### 1. 候选字段（3 个）

| 编号 | 建议字段                                                                                                                                     | 范围                          | 初值（出生时）       | 谁能改                                | 谁读                    |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------- | -------------------- | ------------------------------------- | ----------------------- |
| C1   | `wellbeing.stress: number`                                                                                                                   | 0—1（0 = 放松，1 = 极度紧张） | 0.30，**确定性常数** | 只有本任务的原型运行器                | 原型；M4-016 的「幸福」 |
| C2   | `social.ties: number`                                                                                                                        | 0—1（0 = 孤立，1 = 联系紧密） | 0.50，**确定性常数** | 只有本任务的原型运行器                | 原型；M4-016 的「人际」 |
| C3   | `skills: Array<{ id: string; level: number; since: ISODate }>`（最多 12 条；`id` 取 `interest:*` / `skill:*`，来自固定目录，不允许自由文本） | 每条 `level ∈ [0,1]`          | `[]`                 | 只有本任务的原型运行器（原型 16、17） | 原型；M4-016 的「知识」 |

**为什么是这三个**：

- 现有字段能表达的已经用了：学历（`education.completed`）、就业（`employment`）、慢性病（`health.conditions`）、
  余额与负债（`householdAccounts.balanceMinor`）、关系亲疏（`bonds`）。20 个原型里「友谊/邻里/重聚」只能落在**社交联系**上
  （不实例化朋友角色也能表达），「压力与休息」只能落在**压力**上，「兴趣/新技能」只能落在**技能与兴趣**上。没有别的可借用字段。
- **不新增「近期重大经历的记忆」**（ADR-0010 B 的候选之一）：本任务的 20 个原型都不需要它——「回想一生」「同学重聚」
  都能用年龄与 `education.completed` 表达；M4-016 拿得到事实日志，可以自己按事实价态计算「近期好坏」。
  真需要时再加（那时会改快照结构，属于新的契约变更）。

## 频率预算（用本文的概率表算出）

### 1. 口径与算法

- 目标（V0.1_PLAN §2 的 P1）：**每年可见事件数 ≥ 1.5（pooled 均值）**、**≥ 90% 的在世年份至少 1 条可见事件**。
- 逐年、逐原型的抽样是**独立的伯努利**：约束 6 让每个原型每年拿到一条独立随机流（键 = `life.<原型 ID>|char:protagonist|year:<年份>`），
  `chance(p)` 恰好消耗一次抽样，与结果无关。因此：
  - 某一年可见事件的**期望** `E[N_year] = Σ_{i ∈ 当年可抽} p_i`（线性，不需要独立性假设）；
  - 该年**一条原型事件都没有**的概率 `P(0) = Π_{i ∈ 当年可抽} (1 − p_i)`，是**精确的 Poisson-binomial 乘积**，
    不是二项（各 p 不等）、**也不该用泊松近似**：λ = 1.98 时泊松给出 e^{−1.98} = 13.8% 的空年率，会误判为不达标；
    精确乘积是 6.2%，因为这里的 p 不是稀有事件。
  - 基线（现有的学历/就业/健康/父母 `npc.*` 事实）只会**增加**可见事件，所以 `P(0)` 的乘积是**上界**（保守）。
- **互斥**：v1 **没有**互斥的原型对；互斥只发生在**一个原型内部**（同年只选一个变体）。理由：一旦两个原型互斥，
  空年概率就不再是乘积而是并集，覆盖率的证明要重做。**若将来要加互斥原型，必须做成同一原型的两个变体。**
- **年度上限**：每个原型每年最多一次（`period = year:<YYYY>` 是幂等键的一部分，重复排程被内核去重，结构上不可能同年两次）。
- **一生上限与覆盖的关系**：多数覆盖型原型的 `lifetimeCap` = 资格年龄数（每年最多一次），链条不会因为上限提前终止；
  例外是 6（上限 1）与 16（上限 3），它们到上限后链条终止，**直接**使乘积变大。因此覆盖计算按「1—15 全在链条上」取最坏情况，
  并单独核对「把 6 从乘积里完全去掉」仍然达标：4 岁 0.056、8—11 岁 0.072、12 岁起 0.081，结论不变。
  其余小上限原型（17、18、20）不参与覆盖下界，只影响均值；19 的上限（35）等于资格年龄数。
- **死亡与出生年**：出生年有 `life.birth` 与两条 `family.parent`；死亡年有 `life.death`。两端年份天然非空，
  空年比例只在中间年份受影响。
- 估算时**按 Ages（生日年龄）逐年求值**：年龄 a 对应日历年 = 出生年 + a，所以年代窗口与年龄窗口可以从同一张表逐格计算。

| 原型            | 可抽年龄数 | 期望次数（未截断） | 截断后（上限）    |

于是**每年可见事件数的期望**：

```text
1.983（覆盖型） + 23.50 / 78（风味型，按 78 年在世折算 = 0.301） + 0.2398（现有基线）
= 2.52 条/年（可见事实约 196 条/一生，现状 20 条）
```

空年比例：覆盖型的平均上界 6.22% 已经 ≤ 10%；风味型与基线只会再降低它。**保守结论：期望空年比例约 6%**，P1 的 10% 判据有余量。

### 4. 与 P1 目标的关系（一个必须写进报告的设计发现）

1.5 的均值目标是**下界**，我们落在 **2.52**（超出约 68%）。这不是概率表写「大」了，而是两个目标的**数学张力**：

> 在独立抽样、p 相同、每年龄 n 个原型的模型下，要让 `P(0) = (1 − p)^n ≤ 0.10`，同时 `λ = n·p`，可以解出
> `λ ≥ n·(1 − 0.1^{1/n})`：n = 3 → 1.61；n = 4 → 1.75；n = 5 → 1.85；n → ∞ → **2.30**。
> 也就是说：**只要坚持「≥ 90% 的年份有事件」且抽样独立（约束 6），均值就会被推到 1.6—2.3 之间**；
> 想同时得到「均值 ≈ 1.5」，只能降低覆盖要求（例如 80%），或引入一个「保证事件」机制（一个 p ≈ 1 的原型）。
> 后者违反「概率是设计假设」的直觉，也会让每年都必然发生同一类事件；本任务**不做**，列为「需要维护者决定的问题」1。

本设计每个年龄 3—5 个原型（而不是贴着 3 个的下限），是为了让四个生命阶段各有自己的内容、并且每个原型每个年龄只用一次；
代价就是均值 2.52 与更高的重复率（见 §5）。

### 5. 事件数与性能预算（本任务最大的实施风险）

- 每局**新增事件数** = 覆盖型的可抽年龄数 + 风味型的可抽年龄数：
  30 岁去世 ≈ 227 + 172 = 399；78 岁 ≈ 300 + 196 = **496**；105 岁 ≈ 409 + 196 = 605。
- 现状的事件数按结构推算在 300 量级（80 个主角生日 + 每年的教育/就业/健康等子事件 + 2 个 NPC 各 80 个生日 + 出生/死亡），
  因此**每局事件数约 800**、约 2.6 倍；每次事件引擎都克隆一次状态。**p50 会明显上升**（预计 1.5—2 倍）。
  实施时必须用改前/改后的 `processedKeys.length` 实测值替换这里的推算（见「实现要求 10」）。
- [V0.1_PLAN](../V0.1_PLAN.md) §8 已经预期了这件事（「事件密度提高 5—6 倍……G1 时超过 5.5 ms/局就由道 K 做内核按需复制」）。
  本任务的立场：**不为了性能缩小原型库**；在完成报告里给出前后 `pnpm bench --lives 1000` 的 p50 与 `processedKeys` 计数，
  由维护者决定是否让道 K 先做内核优化（「需要维护者决定的问题」5）。
- 与性能无关但同样要记录的：快照里的 `schedulerState.processedKeys` 会增加约 500 条键（约 +15—20 KB/局），
  M5-001 的 `snapshots.meanBytes` 会随之上升；这是预期变化，不是缺陷。

### 3. 年度排程（`scheduleLifeEventYear`，从 `life.birthday` 调用）

- 只在 `actor.tier === 'protagonist'` 时排程（NPC 不排；见背景 §2）。
- 对目录里**每个**满足「年龄在窗口内、日历年在年代窗口内」的原型，排一条事件：

```ts
ctx.schedule({
  type: lifeEventType(prototype.id), //  'life.first-playmate'
  at: ctx.at, //                       生日当天
  entityId: actor.id,
  period: `year:${year}`, //           键 = type|entity|year → 随机流按（原型, 实体, 年份）隔离
  payload: { count: 0 },
});
```

- 排程**不抽随机数**、不判 `eligible`（那是事件处理器的事）——排程只决定「这一年该不该抽这个原型」；
  这样「当年有哪些原型可抽」是纯函数，可被测试直接枚举。
- 出生当天（`age:0`）也走同一条路径，但没有任何原型的年龄下界是 0，所以不会排任何原型。

### 4. 事件处理器（每个原型一个，由同一个工厂生成）

工厂 `prototypeEvent(prototype)` 返回 `EventDefinition`（`priority = LIFE_EVENT_PRIORITY`，`version = 1`）：

1. `const payload = LifeEventPayloadSchema.parse(ctx.occurrence.payload)`，
   `LifeEventPayloadSchema = z.strictObject({ count: z.number().int().nonnegative(), variant: z.string().min(1).optional() })`。
2. 读 `actor`、`age = ageOn(actor.birthDate, ctx.at)`、`year = yearOf(ctx.at)`；年龄或年代不在窗口内 → `return`（防御，正常不会发生）。
3. `count >= prototype.lifetimeCap` → `return`（链条本应已终止；防御）。
4. `prototype.eligible && !prototype.eligible(input)` → 本年不发生，**继续排下一年**（跳过年份、不终止链条），`return`。
5. **第一次抽样必须是出现判定**：`if (!ctx.random.chance(prototype.annualProbability)) { scheduleNextYear(ctx, prototype, actor, year, count); return; }`
6. 可用变体 = 按目录顺序过滤（变体年代窗口 ∩ 当前年 且 `when(input)`）；若为空 → 排下一年并 `return`（防御）。
7. 选变体：只有 1 个时不消耗抽样；否则 `const index = ctx.random.int(variants.length)`（等权、按目录顺序）。
8. **没有决策**的原型：写后果 + 发事实（见本节末的 emit 约定），然后排下一年（`count + 1`）。
9. **有决策**的原型（两段式，见下）：同一时刻排一条决策事件：

```ts
ctx.schedule({
  type: `${lifeEventType(prototype.id)}.choice`,
  at: ctx.at,
  entityId: actor.id,
  period: `year:${year}:choice`,
  payload: { count: count + 1, variant: variant.id },
});
```

决策事件是一个普通的 `EventDefinition`：`priority = LIFE_EVENT_DECISION_PRIORITY`、`version = 1`、
`decision: { major: false, actorId: (occurrence) => occurrence.entityId, options(input) { ... } }`，
`handle` 里用 `ctx.choice?.optionId` 设 `input.choice`，调用对应变体的 `apply` 并 `emit`，然后排下一年（`count` 用 payload 里的值）。

**emit 约定**（两个处理器共用，写成同一个函数 `emitPrototypeFact`）：

```ts
ctx.emit({
  type: prototype.type, //                              'life.first-playmate'
  outcomeCode: outcome.outcomeCode ?? variant.id,
  templateId: `life.${prototype.id}.${variant.id}`, //  叙事模板键
  actorIds: [actor.id],
  evidenceIds: [], //                                   设计假设，不引用数据表
  ...(outcome.details ? { details: outcome.details } : {}),
  // 不传 causes：原型事实由年度抽样引起，不由其他事实引起
});
```

**为什么两段式**：内核在 `handle` 之前就结算决策并写 `decision.made`。若把决策放在「出现判定」的同一个事件里，
玩家会在事件**没发生**的年份被提问（例如 6—16 岁每年问一次爱好），而且 `decision.made` 会在没有对应事实时留下孤儿记录。
两段式保证：先抽「今年有没有这件事」，只有发生了才问「怎么做」。两段共享同一个随机流键（第一段的键），
第二段不抽随机数。

### 5. 一生上限与链条终止

- `payload.count` 是该原型到这一年的**已发生次数**（不是排程次数）。
- 发生一次后，排下一年用 `count + 1`；没发生用 `count`。
- 链条终止的条件（进入事件处理器时检查或排程时检查，二者取并集）：
  `count >= lifetimeCap`；下一年超出年龄窗口；下一年超出年代窗口；决策原型在当前年没有可用变体。
- 多数覆盖型原型的 `lifetimeCap` = 资格年龄数，上限不会提前切断覆盖；6（上限 1）与 16（上限 3）例外，
  但它们触发上限后对覆盖下界的影响已在「频率预算」里单独核对（结论不变）。其余小上限是叙事上限
  （例如「同学重聚」一生 4 次、「学会新技能」一生 5 次）。
- **每年最多一次**由 `period = year:<YYYY>` 保证：同一年同一原型不可能有两条键，重复排程被内核幂等去重。
