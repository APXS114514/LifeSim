## 目标

让 Tier1 NPC（出生家庭里的父母）过自己的日子：每年生日推进教育/就业/健康/死亡；**死亡后不再产生任何事实**；NPC 的层级可以提升，但已经确定的事实不得重抽。这是 M3-A 的核心：NPC 不是主角的附属字段。

## 背景

- GDD §6.3：Tier1 核心家庭/密友运行连续的教育、工作、健康、关系与重大事件；Tier2 压缩；Tier3 统计。
- GDD §7：不能出现「死亡父亲次年失业」。
- 现有内核：`life.birthday` 只为主角安排年度事件；不变量 `lifeInvariants` 遍历全部角色，所以 NPC 状态必须始终满足年龄资格。
- 命名：本任务**不引入人名**，叙事用关系角色称谓（`role: 'mother'` 等）经 `enums.role` 渲染；M4 再决定是否加姓名。
- 性别未决（Q1）：NPC 不写 sex，不按性别区分概率。
- M3-010 现状（2026-10-21 接手审计核对）：父母由 `family.ts` 在 `life.birth` 里用**出生事件的随机流**生成（在主角的三次抽样之后），没有自己的事件；因此他们永远「在世、在职」。父母各有一个零余额账户，所以历史锚点会为他们各写一条币制换算事实；政体更替也会为他们各写一条事实。这些事实目前使用与主角相同的模板，时间线上看不出是谁（例如连续三条「政治归属随政体更替改为俄罗斯联邦」）。
- 随机流隔离已验证：加入父母前后，300 个种子的主角事实（日期、类型、结果、细节）完全相同。NPC 事件的幂等键含 NPC 的实体 ID，自动获得独立随机流；本任务必须保持这一性质（见验收 7）。

## 实现要求

1. **生日推进**：为每个 Tier1 NPC 安排 `npc.birthday`（事件类型新常量），每年：
   - 教育：沿用 `region.rules` 的学制与 `education` 的概率；NPC 的升学结果独立抽样；
   - 就业：达到工作年龄且未就业/未退休 → 求职；已就业 → 年度失业风险；到退休年龄 → 退休；
   - 健康：沿用 `health.ts` 的发病与死亡公式（**同一次检查定生死与死因**，不得为 NPC 另写一套重复抽样）；
   - 死亡：事实类型仍为 `life.death`（`actorIds: [npc]`），但 `templateId` 用 `npc.death`；之后不再为该 NPC 安排任何事件。
   - 去世时，该 NPC 参与的所有关系把 `coResident` 改为 `false`；`until` 保持 `null`（亲子关系不因死亡解除）。
   - **已故者的账户**：`history.ts` 的币制换算按账户循环，并以账户所有者为 `actorIds`。所有者去世后，内核会以「死后仍参与事实」拒绝该事件，整局报错。处理方式（保守默认）：余额照常换算（`life.currency-version` 不变量要求所有账户使用当前币制），事实写 `actorIds: []`、`templateId: 'npc.estate-redenominated'`、`details` 带 `role` 与换算前后金额。继承与遗产分配不在本任务。
2. **状态一致性**：
   - 死者不参与任何后续事件；事件处理入口先检查 `vitalStatus.kind === 'deceased'` 并直接返回；
   - 未成年人不得就业、未到龄不得退休（不变量已有，必须保持通过）；
   - NPC 的求职失败/失业不得以主角的事实 ID 为原因。
3. **叙事**：NPC 事实的模板键以 `npc.` 开头（例如 `npc.hired`），`details` 里带 `role`；zh/en 模板分别为「母亲找到了工作。」/「Mother found a job.」这类**关系称谓**，不使用第三人称代词。锚点后果（币制换算、政体更替）落到 NPC 身上时同样用 `npc.*` 模板写明是谁（例如「母亲的存款随币制改革换算……」）。
4. **层级提升**：提供 `promoteToTier1(state, actorId)` 的纯函数（Tier2 → Tier1 时才用，M3-017/018 与 M3-030 会调用）；提升只增加排程，不重抽已有字段。
5. **性能**：每个 NPC 的年度事件必须复用主角规则的函数或共享实现，禁止再复制一份概率公式；在报告里记录 `pnpm bench --lives 1000` 的 p50/p99 与事实数量变化。基线是 M3-036 之后的约 **3.0 ms/局**（Apple M5；同一台机器不同时段会有约 ±0.1 ms 波动，务必在同一时段交替测量基线提交与本任务）；p50 超过 **5.5 ms/局** 时停止并报告，不要自行优化内核（内核的按需复制由 Claude Code 另立任务处理）。
6. **证据**：NPC 事实的 `evidenceIds` 只引用真正决定该结果的数据表（例如死亡引用 `mortality`）；D 级常数决定的结果不得引用 B 级表。

## 验收测试

1. 父母在主角 30 岁前至少发生 1 条就业或健康事实；所有事实的 `actorIds` 指向存在的角色。
2. **死者无新行为**：构造一个父母在建档后 3 年内去世的种子（可通过固定 seed 找到），断言死亡事实之后没有任何以该 NPC 为 actor 的事实。
3. 不变量测试：用 fast-check 随机 seed 跑 50 局，断言「未成年人就业」「未到龄退休」「死者有新增事实」三类违规一次都不出现。
4. 确定性：同 seed 两次运行的规范事实指纹相同；快照恢复后继续推进与不中断一致。
5. 叙事：每类 NPC 事实在 zh-Hans 与 en 下都能渲染，且不含 `{{`。
6. 黄金指纹：若变化，报告 `factCount` 与指纹差值并解释——**逐条说明**多出或改变的事实来自哪个事件（M3-010 的提交说明曾把「父母账户的币制换算」误写成「随机流位置变化」，不要重复这种推测）。
7. **主角投影不变**：新增测试，对固定的 300 个种子（出生年份与日期轮换、其中三分之一预选 `start-work`）跑完整人生，只取 `actorIds` 全部为主角或为空的事实，把（日期、类型、结果、`details`）按序拼接后取 SHA-256。**先在实现前的基线提交上运行一次，把得到的值写进测试**，然后再实现规则；实现完成后该值不得改变（NPC 的生活不得改变主角的随机结果）。
8. 去世 NPC 的关系 `coResident === false`，且关系仍通过 `RelationshipsSchema`。

## 完成定义

- NPC 有独立生命周期，死亡后停止；测试通过；性能数字记录在报告里。
- 没有为 NPC 复制一套并行的死亡/职业公式。

## 可能的阻塞（遇到就停止并报告）

- 内核不允许为同一实体安排多个不同周期的事件，或死亡后仍会处理已排队的事件（需要内核改动 → 停下来报告）。
- 性能超过上面第 5 条的预算（p50 > 5.5 ms/局）。
- 现有的出生日顺序假设（主角先、NPC 后）导致事实日期倒流。
