## 背景

- 提交 `713409d` 的 CI（run 39542191274）在 `apps/cli/src/cli.test.ts` 的模板覆盖测试处超时（5 s）。上一次绿灯是 `ee4624d`；中间 M3-001…M3-010 一次推送，CI 没有逐个提交运行。
- 逐提交测量（Apple M5，`pnpm bench --lives 1000`，同一台机器）：

  | 提交                   | p50 ms/局 | 平均事实数 | 快照字节 | 覆盖测试（单独运行） |
  | ---------------------- | --------- | ---------- | -------- | -------------------- |
  | `ee4624d`（绿）        | 1.77      | 76.9       | 12,177   | 926 ms               |
  | `1a9c9e3`（M3-010 前） | 1.82      | 76.9       | 12,177   | 992 ms               |
  | `48ca301`（M3-010）    | 4.34      | 79.4       | 14,734   | 1,490 ms             |
  | `e19901a`（M3-009）    | 4.35      | 79.4       | 14,734   | 1,561 ms             |
  | 本任务                 | 2.72      | 79.4       | 14,734   | 1,142 ms             |

- 剖析（`--cpu-prof`）：退化前后规则处理器只占约 2%；每个事件 49% 在 `#verify`（其中 zod 41%），28% 在 `cloneJson`。`#verify` 对**全部**角色做 schema 解析，角色从 1 个变 3 个，成本近似线性增长。ADR-0004 已预见此事（「M3 引入 NPC 后重新测量」）。
- 结论：是真实的性能退化（不是 CI 波动），根因在内核的按角色总数计费，而不是 M3-010 的规则本身；测试工作量（200 局 + 1 局真实人生，每局各渲染中英）合理，没有重复计算，最长一局 111 条事实，没有异常事件链。

## 实现（已完成）

1. `#verify` 只解析本事件新增或与提交前不同的角色与账户（`jsonEqual` 比较）；复活检查、事实校验与各系统不变量仍每个事件全量执行。正确性依据：已提交状态必然通过过校验（创建时为空，恢复时整份快照经 `SimulationSnapshotSchema` 解析），schema 校验只取决于值本身。
2. `cloneJson` 正常路径不拼接路径字符串；出错时重新遍历一次，错误类型与路径与以前相同。
3. 新增 `jsonEqual`（导出，忽略键顺序）。
4. fast-check 在新性质测试里发现 `cloneJson` 的既有缺陷：自有键 `__proto__` 会被当成原型赋值而丢失数据（M1 起存在，目前不可达：实体 ID 不能以下划线开头，存档信封拒绝该键）。现在改为抛 `TypeError('Unsafe key __proto__ at …')`。
5. `cli.test.ts` 模板覆盖测试单独设 20 s 预算（注释写明测量依据）；其他测试与全局超时不变。
6. ADR-0004 增补「增量校验」一节。
