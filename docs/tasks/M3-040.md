## 背景（Claude Code 审查 M3-034 时发现）

- `GameSession` 在两处用 `simulation.pendingDecision()` 推断「有没有待决事项」：构造函数（新建与读档）与 `#advance()` 的非决定分支（`stopReason` 为 `target-reached`、`protagonist-died` 等）。
- 内核的 `pendingDecision()` **只看队首、不看日期**：只要队首是没有选择的重大决定，就返回它，即使它排在当前时钟之后。
- 现在的重大决定（`choice.after-secondary`）都排在当天，所以这个问题不会触发。但从 M3-017（婚恋）起，规则可能把重大决定排在任意日期；届时「下一年」停在生日后，决定卡会**提前最多一年**弹出，玩家在错误的日期作出选择。
- 正确的语义：只有内核因为这个决定而停下时（`stopReason === 'major-decision'`，此时内核把时钟设为决定日期），或者读档时快照恰好停在这个决定上（决定日期等于时钟），才算待决。

## 实现要求

1. 新增私有方法，例如 `#pendingAtClock(): PendingDecision | null`：调用 `simulation.pendingDecision()`，只有返回值不为空且 `pending.at <= simulation.clock` 时才返回它，否则返回 `null`。
2. 构造函数用它代替直接调用 `pendingDecision()`。
3. `#advance()`：`stopReason === 'major-decision'` 时用 `result.pendingDecision`（现状不变）；其他停止原因一律用 `#pendingAtClock()`（同一天还有第二个决定时仍能正确返回）。
4. 不改任何公开方法的签名与语义；M3-034 的全部测试必须原样通过。

## 验收测试

1. 构造「队首是未来日期的重大决定」而不改规则。注意：内核的 `advanceTo` 内部也调用 `this.pendingDecision()`，直接替换会弄坏推进本身。做法：同时 spy `advanceTo` 与 `pendingDecision`，用一个标志区分调用来源——`advanceTo` 执行期间 `pendingDecision` 调用原实现，其余时候返回一个 `at` 晚于当前 `clock` 的假决定（测试夹具，在测试里标明）：

   ```ts
   let inAdvance = false;
   const advance = session.simulation.advanceTo.bind(session.simulation);
   vi.spyOn(session.simulation, 'advanceTo').mockImplementation((request, token) => {
     inAdvance = true;
     try {
       return advance(request, token);
     } finally {
       inAdvance = false;
     }
   });
   const original = session.simulation.pendingDecision.bind(session.simulation);
   vi.spyOn(session.simulation, 'pendingDecision').mockImplementation(() =>
     inAdvance ? original() : futureDecision(session.clock),
   );
   ```

   断言 `stepYear()` 之后 `session.pending` 为 `null`，且连续 `stepYear()` 能继续推进（年龄逐年增加）。

2. 读档路径：对 `Simulation.prototype.pendingDecision` 做同样的替换（`advanceTo` 未执行时返回未来日期的假决定），断言 `GameSession.restore` 得到的会话 `pending` 为 `null`；测试结束 `mockRestore()`。
3. 决定日期等于时钟时（读档停在决定上的真实场景，沿用 M3-034 已有的存档往返用例），`pending` 仍然不为空。
4. M3-034 的全部单元测试与 E2E 不变且通过。
