## 目标

实现「认识 → 交往 → 结婚 → 分居/离婚/丧偶」的连续路径：伴侣是独立 NPC，有自己的意愿与状态；玩家可以追求但不能强制；婚姻、离婚、丧偶改变关系图、共同居住与家庭结构。**不婚是合法且正常的路径**（GDD §8.4），不得把婚育当作单一成功指标。

本任务不做收养与育儿（M3-018）、不做生育（M3-019）、不做关系动态/玩家干预的完整模型（M3-020）、不做离婚财产分割（M3-014）。本任务只记录「账户是否共享」的现状，不发明分割规则。

## 交付拆分（建议，按道 K / 道 R 分工）

- **M3-017a（契约与规则数据，建议道 K）**：`RELATIONSHIP_KINDS` 扩展、`familyLaw` 规则数据 schema、`FamilyQueries` 接口、`SNAPSHOT_SCHEMA_VERSION` 处理、旧快照非破坏性测试。判定：`pnpm verify` 通过；不改变现有抽样时黄金不变。
- **M3-017b（规则与验收，道 R）**：伴侣 NPC、追求、结婚、离婚、丧偶、姓名变更、叙事、黄金更新。判定见「验收测试」。
- 若合并交付，报告必须分列契约与规则的高风险点，并由维护者审查。

## 背景（现状与已定约束）

### 1. 代码现状（2026-10-22，`main` `8742255`）

- `RELATIONSHIP_KINDS` 目前是 `parent-child`、`adoptive-parent-child`、`sibling`、`spouse`、`former-spouse`；**没有 `partner`**。
- `spouse` 的 schema 规则是 `biological === false` 且 `until === null`；`former-spouse` 是 `biological === false` 且 `until !== null`。因此旧稿「配偶死亡时把 `spouse.until` 置为死亡日」**直接违反现行 schema**：要么新增一种终止后的配偶关系（例如 `widowed-spouse`），要么修改 `spouse` 规则并加 `endReason`；这是本任务必须先解决的契约问题（见「需要维护者决定的问题」5）。
- 关系数组不允许同一角色有多条有效 `spouse`（`until === null`）；`bonds` 必须同时包含双方，`bonds` 的键只能是关系双方；关系有 `legal`、`biological`、`coResident` 三个客观字段。
- `CharacterState` 已有 `sex: 'female' | 'male'`（ADR-0010 A1，统计口径的出生性别，**不是性别认同**）、`name: PersonName`（`scheme` / `family` / `given` / `patronymic`，存表引用）、`lifePrinciples`、`vitalStatus`、`currentResidenceId`。
- `family.ts` 只在出生时创建父母；`npc.ts` 提供 `promoteToTier1`、`npcBirthdayRequest`、`npcRoleOf`（目前只识别 mother/father/relative）。伴侣 NPC 需要创建账户、排 `identity.name` 与 `npc.birthday`，并在 `npcRoleOf` / 叙事里得到「伴侣/配偶」称谓。
- `life.ts` 的 `life.death` 处理器会把死者参与的所有关系 `coResident` 置 false，但**不会**结束 `spouse` 关系；本任务要在死亡处理里加入丧偶逻辑（或由死亡处理器调用 `marriage.ts` 的纯函数）。
- `coResident` 是关系字段，不是婚姻字段。GDD §8.4 明确把法律婚姻、情感关系、共同居住、亲生/收养/抚养责任分开；因此**结婚不应无条件把 `coResident` 置 true**，分居也不等于离婚。
- 婚姻法数据：国家包 manifest 已有 `familyLaw` 模块名，但没有 schema 与数据；`data/sources.json` 没有婚姻法、结婚率或离婚率来源。`family.ts` 的父母年龄/教育是 D 级。
- 性能基线（G1）：约 **842 事件/局、341—342 事实/局、p50 ≈ 5.9 ms**；每事实预算 `p50 ≤ 5.5 × (事实数 / 167)`。见 [V0.1_PLAN](../V0.1_PLAN.md) §4 与 [G1-PERF-PROFILE](../audits/G1-PERF-PROFILE.md)。

### 2. 已定的约束

- **GDD §8.4 / §6.3**：法律婚姻、情感关系、共同居住、亲生亲属、收养与抚养责任分离；双方各有信任、亲密、价值观与冲突状态；玩家可协商不能控制 NPC；支持多次婚姻、收养、监护、亲子、不婚、不育；不把婚育当作单一成功指标。
- **ADR-0010 A1**：角色有 `sex`，但**其他规则不按性别区分概率**，除非有可核验依据并单独审查。部分国家（例如中国大陆、日本 2022 年前）的法定婚龄存在男女差异，属于「可核验的法律规则」；是否采用分性别婚龄、以及配偶性别如何决定，见「需要维护者决定的问题」1、2、9。
- **ADR-0010 A2**：婚后改姓只通过事实发生（本任务实现）：日本妻子随夫姓（法律上的夫妻同姓），俄罗斯妻子取夫姓的阴性形式（表条目自带 `genderedForms`，显示层按角色性别选形），中国大陆/韩国/朝鲜婚后不改姓。主角与 NPC 的姓名都存 `NameRef`，事实的 `details` 不写姓名字符串。
- **史实前提（维护者给定）**：1950—2026 年，五国历史上均未承认同性婚姻。如何处理伴侣性别与这一法律事实，是产品决定，本任务只列选项，不替维护者决定。
- **数据**：结婚率、离婚率、初婚年龄、年龄差、婚姻法条款都没有已登记的可再分发来源。没有来源时只能是 D 级假设，登记在 ADR（建议新 ADR「婚恋与家庭形成」或 ADR-0007 增补）；**不得编造**五国历史结婚率/离婚率。
- **M3-042 / M3-041 边界**：通用事件原型不得创建/结束 `spouse`/`partner`、不得改 `coResident`、不得发 `family.*` 婚恋事实；年度重点没有婚姻/离婚乘数，`family` 只加 `stress`/`ties`，不得直接乘结婚/离婚概率。
- **M3-014**：家庭财务与离婚财产分割归 M3-014；本任务只记录账户是否共享，不发明分割规则。

## 与现有机制的接口

### 1. 年度重点乘数：哪些乘、哪些不乘

`FOCUS_EFFECTS` 没有「结婚」「离婚」「伴侣出现」这类键。本任务的口径：

| 项                                     | 是否乘年度重点       | 说明                                                                  |
| -------------------------------------- | -------------------- | --------------------------------------------------------------------- |
| 遇到潜在伴侣的概率                     | **不乘**             | 没有「重点 → 婚恋机会」的映射；乘了就是没有依据的伪因果               |
| 结婚概率 / NPC 同意阈值                | **不乘**             | 由关系 `bonds`、原则、婚龄与法律决定                                  |
| 离婚概率                               | **不乘**             | 由冲突、经济压力、疾病、婚龄等决定；没有 `FOCUS_EFFECTS` 键           |
| 丧偶                                   | **不乘**             | 由配偶死亡事件决定                                                    |
| `family` 重点                          | 只写 `stress`/`ties` | `focus.complete` 已一次性写入；不得在婚恋事件里重复写或拿它当婚恋乘数 |
| `education`/`hiring`/`jobLoss`/`onset` | 不用于本任务         | 分别归教育/职业/健康；疾病/经济对离婚的影响走各自的状态，不乘重点     |

如果维护者希望「家庭重点更容易结婚/更不容易离婚」，必须先改 `FOCUS_EFFECTS`（新增键）、披露与 M3-041 的测试，并评估决策密度；执行 Agent 不得自行加键或乘概率。

### 2. M3-042 通用人生事件：避免重复、`when` 如何读新字段

- 原型运行器与纯函数约束见 `life-events.ts`：`eligible`、`variant.when`、`topicAvailable` 不抽随机数、不写状态。
- 原型可以**读** `state.relationships`、`actor.sex`、`actor.name`、`actor.vitalStatus`、`actor.currentResidenceId`，用于选择文案变体（例如「与家人过节」vs「独居」），但**不得**创建/结束 `spouse`/`partner`、不得改 `coResident`、不得发 `family.*` 婚恋事实。
- **重复事件**：婚恋事实只能由本任务的 `marriage.ts` 产生；M3-042 的 `family-time`、`friend-contact`、`reunion` 仍只改 `stress`/`ties`/父母 `bonds`，不得顺手写「认识某人」「结婚」的叙事。未来如果要把「认识伴侣」做成通用事件，必须先从本任务删除/合并对应事件，否则同一个伴侣会认识两次。
- v1 默认不改 M3-042 目录；如果为了文案要加 `when` 变体，必须列出原型 id、旧/新谓词、黄金差异、披露行，并经维护者批准。不得新增原型来复制婚恋事件。

### 3. 细状态（`stress` / `ties` / `skills`）

- 关系的主观状态用 `Relationship.bonds: { trust, intimacy, conflict } ∈ [0,1]`（双方各一条），不是 `social.ties`。
- 本任务写 `bonds`（相处、冲突、支持、分手、离婚后的感受），**不写** `social.ties`（那是 M3-042/年度重点的全局细状态）、不写 `stress`、不写 `skills`。
- 结婚/离婚/丧偶对全局幸福的影响，若需要，应通过 `indicators.ts` 的负面/正面事件集合或关系 `bonds` 派生，不在本任务直接写 `wellbeing.stress`。若维护者要求额外写压力，需在 ADR-0010 B 范围内单独批准。

### 4. 学制与成年

- 结婚年龄、成年与「是否独立」是不同概念：结婚年龄读 `FamilyQueries.minimumMarriageAge(year, sex)`，不读 `educationStageAges`，也不要用「中学毕业」推断成年。
- 付款方/费用用 `isIndependent(actor, age, region)` 与 `RegionRules.minimumWorkingAge`；不得写死 18 岁。

### 5. 「未独立时由家里承担」的金钱规则

- 本任务默认不新增婚礼、彩礼、嫁妆、离婚诉讼等费用（没有数据，也容易变成文化刻板印象）。若确实要一笔婚礼/登记费用，必须是 D 级假设，并复用 `tuitionPayers` 的付款方规则：有自己收入用本人账户，否则用在世父母，不能让孩子/学生因结婚事件负债。
- 离婚财产分割不在本任务：只记录「账户是否共享」的现状；不得自行设定共同财产比例或分割公式。共同账户/家庭层记录归 M3-014。
- 共同居住（`coResident`）与账目分开：结婚不自动合并账户，也不自动把 `coResident` 置 true。

### 6. 每事件成本（G1 预算）

| 项             | 预算                                                                                                       |
| -------------- | ---------------------------------------------------------------------------------------------------------- |
| 新增事件       | **≤ 120 个/局**（未婚成年人的年度「遇到潜在伴侣」检查 1 条/年；找到伴侣后多一个 Tier1 NPC 的年度生日事件） |
| 新增事实       | **≤ 40 条/局**（相识、交往、结婚/拒绝、离婚、丧偶、伴侣 NPC 的生日事实）                                   |
| 相对事实数变化 | 预计 **3—8%**；若 > 10%，按 V0.1_PLAN §4 重测并更新阈值                                                    |
| 实测           | 实施后给出 `pnpm bench --lives 1000` 的 p50/p95 与 `processedKeys.length`，与改前对照                      |

如果实现成「每个成年人每年多条社交/求婚事件」，会超出预算；必须把「遇到潜在伴侣」压成每年至多 1 条事件，且只在未婚/无有效伴侣时排。不得为了性能删掉不婚路径或降低 NPC 自主性。

**关系不变量（在现有 `RelationshipsSchema` 与 `life.relationship-actors` 之外新增）**：

1. `partner`：同一角色最多一条有效（`until === null`）的 `partner`；若维护者允许同时多个，必须改本规则并说明（见「需要维护者决定的问题」4）。
2. `spouse`：同一角色最多一条有效 `spouse`（现有）。
3. 同一对角色不能同时有有效 `spouse` 与 `partner`；结婚时先把 `partner` 置 `until = 结婚日`（或结束关系），再建 `spouse`。
4. 死者不得创建新的 `spouse`/`partner`；配偶死亡后，原 `spouse` 必须转为终止关系（方案 A 的 `widowed-spouse` 或方案 B 的 `until`），不得保留有效 `spouse`。
5. 离婚后同一对角色不能直接恢复有效 `spouse`；再婚必须新建关系（可以有新的 `since`，并保留旧的 `former-spouse`）。
6. `coResident: true` 的关系双方都必须是活人（现有 `life.deceased-no-new-activity` 已覆盖死亡；离婚/丧偶要显式置 false）。

**版本与兼容**：

- 只扩展 `RELATIONSHIP_KINDS` 时，旧快照（没有 `partner`/`widowed-spouse`）仍能被新代码读取；新快照在旧代码上会被 schema 拒绝，按 Q9 非破坏性处理。**不新增持久字段时原则上不提升 `SNAPSHOT_SCHEMA_VERSION`**；若采用方案 B（给 `spouse` 加 `endReason` 或改字段），则必须提升。
- 若 M3-013/015 已经提升过快照版本，本任务与它们合并排期，避免连续作废存档（见「需要维护者决定的问题」11）。
- `SYSTEMS_VERSION` 提升一次；黄金/投影/工作量指纹变化逐条解释。
- 旧事实的 `evidence.modelVersion` 保留当时数据版本；不得用新婚姻法数据改写旧事实。

## 实现要求

1. **关系种类与规则**：加 `partner`；按维护者选择实现丧偶关系（方案 A `widowed-spouse` 或方案 B `spouse.until + endReason`）；更新 `RelationshipsSchema` 的跨字段规则与数组不变量；加测试。
2. **伴侣 NPC**：成年（`age >= FamilyQueries.minimumMarriageAge(year, sex)`）且未婚/无有效伴侣时，每年至多一次「遇到潜在伴侣」抽查（事件键含主角与年份，独立随机流）。命中后创建 Tier1 NPC（ID `char:<主角>:partner-1`，再婚序号递增），带年龄、性别、学历、职业（M3-013）、健康、人生原则、账户；排 `identity.name` 与 `npc.birthday`；建立 `partner` 关系与双方 `bonds`。**不得**在之后升级时重抽这些字段（`promoteToTier1` 只改 tier）。
3. **伴侣性别**：按维护者决定实现（见「需要维护者决定的问题」1/2）。默认**不**自行假设；如果采用「异性伴侣」方案，则在创建时按主角 `sex` 取相反性别；如果采用「伴侣性别独立」方案，则按 D 级比例抽取并在披露里说明；如果允许同性法律婚姻，必须同时处理婚姻法与姓名规则，且与「1950—2026 五国均未承认同性婚姻」的史实前提冲突，需维护者明确承担。
4. **交往与分手**：`bonds` 随相处、冲突、支持事件变化；冲突超过 D 级阈值时可能分手（`partner` 的 `until` 置为当天，发 `family.courtship-ended`），不产生 `spouse`/`former-spouse`。不得用年度重点直接乘分手概率。
5. **结婚**：满足婚龄与 `bonds` 阈值后，给主角排**重大决定**（`major: true`），选项 `marry` / `wait` / `never`（或 `end`）；`never` 只表示「不与当前伴侣结婚」，**不是全局不婚开关**，不写全局标志；不婚路径仍由「没有有效 `spouse`」表达（见「需要维护者决定的问题」6）。NPC 是否同意由它自己的 `bonds`、原则与状态决定（确定性阈值或独立事件流，不得无条件接受）。同意后：结束 `partner` 关系、建立 `spouse`（`until: null`、`legal: true`、`biological: false`）、按同住情况设置 `coResident`、按 ADR-0010 A2 改姓（仅异性婚姻的 `ja`/`ru`；同性方案另行决定）、发 `family.married`（details 含 `spouseId`、`marriageAge`、`nameChanged` 布尔；不写姓名字符串）。拒绝发 `family.marriage-refused`，关系图不产生 `spouse`。
6. **离婚**：冲突、经济压力（`isPoor`）、疾病、婚龄等因素提高 D 级离婚概率；离婚发 `family.divorced`，把 `spouse` 转为 `former-spouse`（`until` 为离婚日）、`coResident: false`；不分割财产，只记录账户是否共享的现状。离婚后同一对角色不能直接恢复有效 `spouse`。
7. **分居**：`coResident: false` 但仍是 `spouse`；v1 不做单独的「法定分居」状态。若维护者要求，另立决定与字段。
8. **丧偶**：配偶死亡时结束 `spouse`（方案 A 转 `widowed-spouse`、`until` = 死亡日；方案 B 置 `until` + `endReason: 'death'`）、`coResident: false`，发 `family.widowed`（cause 指向配偶死亡事实）；此后不再为该配偶排任何事件。死者不发起婚恋事件。
9. **不婚**：不引入 `marriageIntent` 字段；「不婚」= 没有有效 `spouse`，可以由「没有遇到伴侣」「拒绝所有求婚」「选择 `never`」等路径产生。固定种子批量里必须存在不婚角色，报告比例；不得把不婚当成失败。
10. **姓名变更**：只通过事实改 `name.family`；`ja` 妻子取丈夫的姓，`ru` 妻子取丈夫姓条目的阴性形式（显示层按性别选 `genderedForms`），`zh`/`ko`/`kp` 不改；主角与 NPC 同规则。事实 details 不写姓名字符串。
11. **NPC 与升级**：伴侣创建时就是 Tier1；若未来从 Tier2 提升，`promoteToTier1` 只改 `tier`，不重抽出生日期、性别、教育、职业、健康或原则；升级后补排 `npc.birthday`。
12. **叙事、双语与随机流**：新增事实全部 zh-Hans/en；相识/交往/结婚/拒绝/离婚/分居/丧偶模板与 `enums`；随机流按事件键隔离，新增伴侣创建不得移动既有出生/生日抽样；同 seed 两次运行逐字节相同。
13. **版本、黄金与性能**：提升 `SYSTEMS_VERSION`；黄金/投影/工作量指纹变化逐条解释；`pnpm bench --lives 1000` 实测事件数与 p50，超预算先改设计（例如降低「遇到伴侣」频率），不得删不婚路径或降低 NPC 自主性。

## 可能的阻塞（遇到就停止并报告）

1. **关系契约无法表达丧偶**（`spouse.until` 被禁止，且维护者尚未选择 `widowed-spouse` 或 `spouse.until + endReason`）：停止，报告两个方案与影响；不要自行改 schema。
2. **配偶性别/同婚方案未决定**：停止在契约与 NPC 创建之前，报告选项；不要默认异性或默认同性。
3. **婚姻法/结婚率/离婚率没有可登记来源**：用 D 级假设并披露，不要编造精确历史数值；若维护者要求 C/B 级，先登记来源与许可。
4. **快照版本或关系枚举变更未获批准**：按 Q9 非破坏性处理；不要写迁移器或静默默认值。
5. **事件数超出预算**：先检查是否每年排了多条婚恋事件；降低频率或合并事件，不要删不婚路径或降低 NPC 自主性。
6. **姓名变更规则与事实不一致**：先改 ADR-0010 A2 的规则或停止；不要让事实写姓名字符串。

## 需要维护者决定的问题

1. **伴侣的性别**（核心问题）：A. **只生成异性伴侣**（与 1950—2026 五国法律婚姻的史实一致；同性关系不建模）；B. **伴侣性别与主角性别独立**（允许同性情感/同居关系，但法律婚姻仍只限异性，因为五国历史上均未承认同性婚姻）；C. **允许同性法律婚姻**（与史实前提冲突，等于改写宏观法律事实；GDD §2 决定 06 要求真实历史固定，需要维护者明确承担）；D. 按玩家设置/出生设置选择（需要界面与存档字段）。本稿不选，只列选项。
2. **同婚与史实的处理**：如果选 B/C，需要明确：同性伴侣能否登记结婚、能否收养（M3-018）、姓名如何变更、宗教/社会态度是否影响 NPC 同意、以及是否在界面披露「这是产品范围而非史实」。若坚持「五国历史上均不合法」，则只能走 A 或 B（B 不登记法律婚姻）。
3. **`sex` 的口径**：ADR-0010 A1 的 `sex` 是**出生统计性别**，v0.1 不模拟性别认同。若伴侣性别/婚姻规则要使用性别认同，需要新的产品决定与 ADR；本稿不引入。
4. **是否允许多个伴侣/同时交往**：本稿默认「同一角色最多一条有效 `partner`」；若允许同时多个，需要改关系不变量、叙事与测试。
5. **丧偶的关系表示**：A. 新增 `widowed-spouse`（保留「丧偶」与「离婚」的区别，推荐）；B. 允许 `spouse.until` 非空 + `endReason: 'divorce' | 'death'`（少一个枚举，但改 `spouse` 语义并加字段）；C. 保持 `spouse` 有效、另存丧偶状态（会让「有效配偶」与「已故配偶」混淆）。本稿默认 A，但需要 ADR/契约决定。
6. **不婚的表示**：A. 不引入字段，「拒绝所有求婚/没有伴侣」即不婚（本稿默认）；B. 新增 `marriageIntent: 'open' | 'never'` 之类字段（契约与快照变化，但能表达主动不婚）；C. 在界面提供「不婚」预设但不入状态。请选择。
7. **离婚率数据来源**：目前没有已登记的可再分发序列。候选：UN World Marriage Data、UN Demographic Yearbook、各国统计年鉴；需要逐数据集核验许可、口径（粗离婚率 vs 分年龄）与年份覆盖。若都不满足，是否接受 D 级年代化假设并在界面披露？请指定来源或接受 D。
