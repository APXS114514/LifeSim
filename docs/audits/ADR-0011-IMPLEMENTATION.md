# ADR-0011 事务草稿按需复制实现报告

状态：内核实现与验证完成，在 `task/ADR-0011-copy-on-write` 上本地提交；属于模拟内核高风险变更，**待维护者审查后合并**，尚未推送。

## 行为

- 新增内核私有的 `packages/simulation-core/src/draft.ts`（不从包入口导出，无新依赖）。每个事件的处理器拿到一棵 `Proxy.revocable` 草稿：读取共享已提交状态；第一次写某个对象时才浅复制它，并沿父节点向上标记。数组的 push、splice、索引、length、reverse，属性删除和整个分支替换都经由同一组 trap 落在副本上。
- 提交时只为改过的分支生成新的普通 JSON 对象，没改过的分支沿用已提交对象的引用。处理器在本事件里新建并放进状态的对象，提交时深复制（其中引用到的草稿换成它的提交结果），所以处理器之后再改自己的对象，改不到已提交状态。
- 事务结束（成功或失败）时撤销全部代理：处理器留在外面的草稿引用再读写都抛 `TypeError`。
- 非 JSON 值（非有限数、undefined、稀疏数组的空位、函数、Map 等非普通对象、`__proto__` 键、循环引用）在提交时记下第一处及其路径。内核先跑原有的事实、schema、生死与系统不变量检查，保持原来的错误码；都通过后再以 `handler-failed` 拒绝这一处非 JSON 值。直接给草稿赋 `__proto__` 键在写入时就抛错。
- `#verify` 用引用判断「没改动」：没写过的角色、账户和关系图与已提交状态是同一个对象，跳过 schema 解析；`jsonEqual` 不再用于事务。改过的角色与账户仍逐个解析，关系图有变化仍整体校验，系统不变量仍逐事件执行。
- `DecisionSpec.options()` 的丢弃式深拷贝与纯函数检查保持不变（ADR-0011 第 6 条）。决定在处理器之前结算，此时草稿没有写入，所以直接从已提交状态复制，不穿过代理。
- 快照格式、随机流、事实 ID、事件键、调度顺序、`ENGINE_VERSION`、`SNAPSHOT_SCHEMA_VERSION` 与 `SYSTEMS_VERSION` 都没有变。

### 比旧实现更严格的两处

在同一个探针模块上分别跑旧内核（`552d1d4`）与新内核，实测：

| 情形                                                 | 旧内核                                                                   | 新内核                                                                          |
| ---------------------------------------------------- | ------------------------------------------------------------------------ | ------------------------------------------------------------------------------- |
| 处理器保存 `ctx.actor(...)` 的引用，事件提交后再写它 | 写入成功，已提交状态被改成 `place:after-commit`，绕过全部校验            | 抛 `TypeError`（代理已撤销），已提交状态不变                                    |
| 处理器往 `world` 写入 `NaN`                          | 事件提交成功；之后 `snapshot()` 抛未包装的 `TypeError`，存档已经无法生成 | 该事件以 `handler-failed` 拒绝并回滚（含种子、事件键、日期），`world` 仍为 `{}` |

旧内核把草稿直接设为新的已提交状态，所以第一种情形是真实存在的漏洞；现有规则没有触发它（全部事实与快照逐字节不变）。这两处正是 ADR-0011 第 3 条要求的行为。

- 新增 `draft.test.ts`（9 项）：只读不复制、只复制写过的路径、数组 push/splice/索引/length/删除、数组内移动后的身份、插入新对象后继续修改、分支替换与新对象里引用草稿、六类非 JSON 值与 `__proto__`、关闭后撤销；另有 fast-check 300 次随机编辑序列，与「整份深拷贝后就地修改」的旧事务对照，按插入顺序序列化后逐字节相同（键顺序也相同），且已提交状态不变。

## 性能

同一台 Apple M5（10 核，16 GiB，Node 24.21.0）空闲时交替运行旧 main `552d1d4` 与本分支各 3 次 `pnpm bench --lives 1000`，不与浏览器或完整测试并行：

| 版本            | p50 ms/局             | p95 ms/局             | p99 ms/局             | 事实数  | 平均快照 | 工作量指纹                       |
| --------------- | --------------------- | --------------------- | --------------------- | ------- | -------- | -------------------------------- |
| 旧 main 552d1d4 | 6.583 / 6.620 / 6.636 | 7.807 / 7.786 / 7.826 | 8.204 / 8.469 / 8.275 | 167,201 | 23,420 B | 84432c86f0fa2a5718f2ed242660a7f7 |
| ADR-0011        | 4.244 / 4.256 / 4.271 | 5.091 / 5.054 / 5.104 | 5.411 / 5.402 / 5.541 | 167,201 | 23,420 B | 84432c86f0fa2a5718f2ed242660a7f7 |

p50 中位数从 6.620 降到 4.256 ms/局（约 −35.7%），p95 从 7.807 降到 5.091 ms/局。事实数、平均享年 76.4、平均快照字节与工作量指纹完全相同。中位数那一次的完整报告：[改动前](benchmarks/ADR-0011-before.json)、[改动后](benchmarks/ADR-0011-after.json)。

G1 要求 p50 ≤ 5.5 ms/局：**在这台 Apple M5 上**，旧 main 不通过（6.62），本分支通过（4.26）。交接文档里的 AMD EPYC 9V74 云主机没有重新测量；按 ADR-0011 的要求，不把这台机器的绝对耗时当作云主机或其他机型的结果。M3-042 会提高事件密度，届时须在同一台机器上重新做前后对比。

## 审查要点与剩余风险

- 高风险：模拟内核（`engine.ts` 与新增 `draft.ts`）。本报告不代表已完成架构审查。
- 代理只处理普通对象与数组。处理器若对状态调用 `Object.freeze`、`Object.setPrototypeOf` 或写 symbol 键，现在会在该事件内抛错并回滚。以前冻结的对象照常复制，改过原型的对象到下一次拷贝才报错，symbol 键在下一次拷贝时被悄悄丢掉。现有规则都不这样做。
- 处理器若把同一个草稿对象放到状态里的两个位置，提交后两个位置共享同一个普通对象（旧深拷贝事务在同一事件内也同样别名，下一次拷贝时才断开）。之后的事件一写就会分别复制，不会互相影响，快照序列化也不受影响。
- 处理器之外的只读路径（`simulation.state`、`snapshot()`、决定选项视图、存档）仍用 `cloneJson` 复制，所以界面与 Worker 拿到的仍是独立的普通 JSON。
- 没有新增依赖，没有修改阈值、事件、概率、年龄窗口、属性测试次数或不变量。
