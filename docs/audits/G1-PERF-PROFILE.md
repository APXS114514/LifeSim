# G1 性能门禁：模拟内核热点剖析与优化（2026-10-22）

G1 的验收线是 `pnpm bench --lives 1000` 的 `timing.perLifeMs.p50` ≤ 5.5 ms（[V0.1_PLAN](../V0.1_PLAN.md) §4）。
M3-042 把每局事实从 167 条提到 341 条之后，main `d0e9f95` 的 p50 回到 9 ms 上下。
本文件记录热点证据、改动清单、可观察行为不变的论证，以及实测数字。

## 1. 方法与一次性产物

- 机器：Apple M5（10 核）、16 GiB、Node 24.21.0（`node_modules/node`）。
- 采样：`node --cpu-prof --cpu-prof-dir=$TMPDIR apps/cli/src/bench.ts --lives 300`，
  取出 `samples`/`timeDeltas`，按「帧自身时间」汇总（内联帧会记在调用者上，所以份额是采样比例、不是精确计时）。
- 计数：临时在 `#processHead`、`#verify`、`readMacro`、不变量、`isISODate`、`ageOn`、`DraftTransaction` 上各加一个计数器跑 300 局，
  得到「每局各操作的调用次数」，用来把单次成本（微基准）换算成每局开销。
- 剖析脚本与产物都在 `$TMPDIR`，不进仓库（一次性工具，避免把 Node 版本相关的分析器塞进脚本目录）。

## 3. 改动

### 3.1 日期解码：一次扫描代替正则 + 切片（`primitives.ts`、`calendar.ts`）

`decodeISODate()` 按字符码扫描固定宽度的 `YYYY-MM-DD`，合法时返回 `YYYYMMDD` 整数，否则 `-1`；
`isISODate()` 变成 `decodeISODate(v) >= 0`，日历层的 `codeOf()` 直接用它取年、月、日。

- 等价性：接受的字符串集合与 `^(\d{4})-(\d{2})-(\d{2})$` 加日期范围检查逐值相同。
  `primitives.test.ts` 里保留一份正则参考实现，用性质测试把两者锁在一起（任意字符串 + 1—9999 年的真实日期）。
- `calendar.ageOn()` 不再构造 `addYears()` 的结果字符串：同一年内比较（月、日）即可，
  2 月 29 日出生且目标年是平年时按 28 日比较，与 `addYears()` 的落点逐日相同。
  既有的性质测试（`ageOn(birth, addYears(birth, k)) === k` 且前一天是 `k-1`）继续通过。
- 抛错行为不变：非法日期仍是 `RangeError('Not a calendar date: …')`。

### 3.2 决策选项：整份深拷贝改为按需复制（`engine.ts`）

`DecisionSpec.options()` 拿到的不再是 `cloneJson(state)`，而是一份**丢弃式**的 `DraftTransaction` 草稿：
读共享已提交状态，写入落在草稿里（与深拷贝的可见性相同），调用一结束就 `close()`、什么都不提交。
ADR-0011 第 6 条要求的语义（选项只能取决于当前状态、改不到权威状态）不变；
`impure-decision-options` 的随机数/emit/schedule 拦截照旧。

### 3.3 随机流按需派生（`engine.ts`）

`ctx.random` 改成惰性 getter：只有处理器真的抽样时才 `deriveStream(seed, key)`。
派生只取决于（根种子、事件幂等键），与读它的时机无关；不读就不派生，随机序列与消耗次数都不变。

### 3.4 宏观状态按引用缓存（`systems/module.ts`）

`life.currency-version` 不变量每个事件都 `MacroStateSchema.safeParse(state.world)`。
内核保证提交后的状态不再就地修改，所以同一份 `world` 对象的解析结果与合法性只取决于它自己：
按引用缓存（`WeakMap`，随本模块实例存活，一局人生里宏观状态只在历史锚点处改变）。缓存的是**解析结果本身**，
没命中时仍走原来的 `safeParse`，判定与错误信息不变。

### 3.5 角色按字段校验（`character-state.ts`、`engine.ts`）

`#verify` 以前只要角色对象换了引用就整份 `CharacterStateSchema.safeParse`（每局 195 次）。
现在：

1. 提交后没改过的分支与已提交状态是**同一个引用**（ADR-0011），所以按引用比出「本事件真正改过的字段」；
2. 只对改过的字段跑**同一份**字段 schema（`CharacterStateSchema.shape`）；
3. 跨字段规则（学历与就业一致、技能不早于出生、死亡日期不早于出生）抽成单一实现
   `characterStateViolations()`，`CharacterStateSchema` 的 `superRefine` 与内核都调它，整份新角色上**始终**重跑；
4. 键集与 schema 不符（strictObject 的未知键、删字段）、字段不合法、或跨字段违规时，退回整份
   `CharacterStateSchema.safeParse`，**报错信息与以前逐字相同**（慢路径只在真出错时走）。

等价性论证：schema 校验只取决于值。没改过的字段与已提交角色是同一个引用，而那些值在写入时已经通过过完整校验；
改过的字段用同一份字段 schema 校验；跨字段规则在整份新对象上重跑；键集单独核对。
因此「逐字段通过 + 键集一致 + 跨字段规则通过」⟺「整份 `CharacterStateSchema` 通过」。
`engine.test.ts` 新增两例锁定这条路径：单字段非法（`stress: 2`）与 actor 多出 schema 之外的键都必须被拒绝。

## 4. 未采用的候选（实测后放弃）

- **草稿读路径改为「读到即记住、不复制父对象」**（每个已提交对象只造一个草稿代理）：
  与 `main` 交替各 3 次，p50 无差异、p95 反而更差（+1.5 ms），已回退。草稿成本的主要来源是代理本身的
  `get` 开销与节点数量，不是父对象的浅副本。
- **`Proxy.revocable` 换成普通 `Proxy` + 关闭标志**、**把 `#read` 内联进 `get` 陷阱**：交替测量无差异（±0.3 ms 噪声内），
  为减小内核对高风险路径的改动量，未采纳。

## 5. 实测（并行负载下，只用于「改前 vs 改后」对照）

## 6. 剩余热点与下一步建议

改后的自身时间构成（300 局、并行负载）：`simulation-core` 53.0%（其中草稿代理约 18%、引擎约 10%）、
zod 15.5%（几乎全是事实与账户的 schema 解析）、`systems` 15.2%、GC 6.4%、`content-schema` 1.8%。
每局 842 个事件里只有 332 个产生事实，所以进一步提速只能从**每事件固定开销**下手：

1. **草稿代理（每事件 7.4 个节点、约 1.1 ms/局）**：节点来自处理器读到的每个对象。
   最有希望的是让 `ctx.actor(id)` 用已提交数组的原始对象定位下标、再只取那一个草稿（省掉为每个候选建代理），
   需要给 `DraftTransaction` 加一个只读的「已提交基对象」入口（本轮未做，属于新的内核接口）。
2. **事实校验（每局 332 次 `SimEventFactSchema`，约 0.7 ms）**：事实由内核从处理器给出的输入构造，
   输入本身已经过行为约束；要再省必须改契约（例如给处理器一个受控的事实构造器），属于契约层决定。
3. **每事件不变量**：5 个不变量各扫一遍角色/账户/关系（合计约 3%），单次都很便宜，收益有限。
4. 若上述两条都不做，G1 的 5.5 ms 需要在空闲机器上确认；若仍不达标，建议由维护者决定放宽阈值
   （M3-042 把每局事实从 167 条提到 341 条，5.5 ms 是在 167 条的规模下定下的）。
