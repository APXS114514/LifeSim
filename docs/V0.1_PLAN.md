## 3. 分道与关键路径

同一时间每条道只有一个写入者；不同道改的文件不重叠，可以并行（各用独立 worktree）。

```text
道 K  Claude：内核/契约/ADR/高风险审查
      ADR-0008 介入策略 ─ ADR-0009 已知事实 ─ Q14 购买力接口 ─（按需）内核按需复制
道 R  规则队列（DeepSeek，严格串行）
      M3-011 → M3-038(规则) → M3-012 → M3-013 → M3-015 → M3-016 → M3-014
      → M3-017 → M3-018 → M3-020 → M3-030 → M3-021 → M3-019 → M3-022
      → M3-023 → M3-024 / 025 / 026 / 027（逐个）→ M3-028 → M3-029 ══ G2
道 W  网页（DeepSeek，只改 apps/web）
      M3-034 →〔D2 批准后〕M4-001 → 002 → 003 → 004 → 005 → M3-037(界面)
      →〔G2 后〕M4-006 → 007 / 008 / 010 → 012 → 009 → 011 → 013 → 014 ══ G3
道 D  数据（需要联网，逐个）
      M3-039 城市与地区 →（Q1=B 时）分性别生命表 →（Q7=A 时）分年龄生育率
道 Q  质量与发布（M5）
      M5-001 现在可开始 → M5-002 → 〔G2 后〕M5-003 → 〔G3 后〕M5-004 / 005 / 006 / 007 → M5-008 ══ G4
```

**为什么规则道必须串行**：每个规则任务都会提升 `SYSTEMS_VERSION`、可能改变黄金指纹，并改动 `shared.ts` / `narrative.ts` / `module.ts` 这几个热点文件；并行只会制造冲突与无法解释的指纹差异。

**跨道协调点**：

- M4-006 需要在 `packages/systems` 新增 `indicators.ts`：安排在规则道两个任务之间的空档执行，或由规则道代做这一个文件。
- M3-037 的内核部分（道 K）先合并，界面部分（道 W）再做。
- M3-039 改出生选择，会改变所有真实人生：只能在规则道两个任务之间合并，并在报告里说明指纹变化。

## 6. 分工与交接流程

```text
骨架任务 ─► 执行 Agent 细化成完整任务文件 ─► Claude Code 审查任务文件（高风险另需维护者确认）
        ─► 执行 Agent 在新会话按 FLASH_AGENT_PROMPT 实施 ─► 自动化测试
        ─► Claude Code 审查高风险代码 ─► 维护者验收与逐次推送批准
```

| 角色           | 负责                                                                       |
| -------------- | -------------------------------------------------------------------------- |
| 维护者         | 第 7 节的产品决定、门禁验收、高风险合并、**每一次推送**                    |
| Claude Code    | 道 K；骨架与细化后任务文件的审查；高风险代码审查；性能与指纹异常的根因分析 |
| DeepSeek Flash | 骨架细化；道 R、W、D、Q 的实施（一次一个任务、新会话、按任务文件执行）     |
| 自动化测试     | 确定性、不变量、数据来源与许可、存档往返、双语一致、性能基准               |

**细化规则（执行 Agent 把骨架写成完整任务时必须遵守）**：

1. 按 [INDEX「编写新任务的模板」](tasks/INDEX.md) 写全：风险、前置依赖、涉及模块、必读文件、允许/禁止修改、实现要求、验收测试（关键计算给输入输出示例）、验收命令、完成定义、可能的阻塞。
2. **不得改动骨架里「已定的约束」**：风险等级、依赖、允许修改的包、契约方向、数据与证据规则。认为骨架有误时写进「可能的阻塞」并报告，不要自行改。
3. 只能细化纯实现细节（函数划分、文件名、测试用例、文案草稿）。凡是影响公共契约、状态归属、随机流、数据语义或产品范围的选择，列为「需要维护者决定」，给出选项，不选。
4. 每个验收要点都要落成可执行的测试或命令；性能类任务写明基线提交与停止线。
5. 细化本身只提交任务文件（`docs/tasks/<ID>.md`），不改代码；提交后等待审查，审查通过才能开始实施。

**细化提示词**（交给执行 Agent，把 `{{ID}}` 换成任务编号）：

> 你是 LifeSim 的任务规划助手。只做一件事：把骨架任务 `docs/tasks/{{ID}}.md` 细化成可以直接交给执行 Agent 实施的完整任务文件。先读 `AGENTS.md`、`docs/V0.1_PLAN.md` 第 6 节、该骨架文件，以及骨架「必读」里列出的文件；不要通读 GDD 或其他任务。遵守第 6 节的细化规则：不改「已定的约束」，不替维护者做决定，验收要点全部落成可执行测试。只修改 `docs/tasks/{{ID}}.md`，本地提交（不推送），然后输出：细化后的文件摘要、你认为需要维护者决定的问题、你发现的骨架问题。完成后停止。

## 8. 主要风险

- **规则道串行是关键路径**：其他四条道必须充分并行；规则任务保持一个 PR 大小，避免长期阻塞。
- **NPC 规模与性能**：每个事件仍深拷贝整份状态；G1 时超过 5.5 ms/局即由道 K 改为按需复制或结构共享（ADR-0004 已预留）。
- **数据缺口**：朝鲜的教育、CPI、卫生数据全缺；城市人口数据许可未核验。按 GDD 回退与披露，不编造。
- **敏感历史内容**：朝鲜、赴台湾路径、南→北迁移都受 Q10 约束；M3-033 设计稿须先修订史实。
- **包体积**：五国数据约 4.2 MB 进首包，M4-012 按需加载；PWA 缓存策略依赖它。
- **CI 只在推送 `main` 时运行**：一次推送多个任务会让问题无法定位。每个任务单独验证、单独推送；M5-001 增加夜间批量回归。
