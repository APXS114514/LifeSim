# 0004：确定性模拟内核的设计

- 状态：已采纳
- 日期：2026-10-20

## 背景

GDD 把「相同种子加相同输入，结果不一致」和「快进与逐年推进结果不一致」都列为 P0（§14.1），并要求原子结算、事件幂等、循环检测、可恢复的随机状态（§4.1、§7、§11.4）。本 ADR 记录 M1 内核（`packages/simulation-core`）为此做的选择。

## 决定

1. **一个推进器，全序事件队列。** 所有推进方式都调用 `advanceTo`。事件按（日期、优先级、幂等键）排序，与插入顺序、调用如何切分无关。处理器只能读事件日期 `ctx.at`，读不到推进器的时钟。
2. **计数器式随机流。** 每个事件的随机流由「根种子 + 事件幂等键（类型|实体|时段）」散列派生（四路乘法散列加 fmix32 收尾，生成器为 sfc32）。无关事件的顺序、分批推进的切分都不会改变某个事件拿到的随机数。因为不存在跨事件的流状态，快照的 `rngState` 只记录算法版本；改算法必须提升 `RNG_ALGORITHM`，并有黄金值测试锁定。
3. **确定性数学。** 风险换算用自己实现的 `expDet` / `lnDet`，只用 IEEE 754 正确舍入的四则运算与 `Math.round`，避免各 JS 引擎 `Math.exp` / `Math.log` 末位不同，导致同一存档在不同浏览器里走向不同结局。
4. **草稿—校验—提交。** 每个事件在状态的深拷贝上处理；事实结构、角色与账户的 schema、时间与生死约束、各系统的不变量都通过之后才整体提交。处理器抛错或检查失败时，状态与队列都保持原样，并抛出带种子、事件键与日期的 `SimulationError`。
5. **幂等与失控检测。** 同一幂等键已在队列中时，再次安排会被忽略；已经处理过的键再次被安排，视为事件循环并报错。另有硬上限：同一天最多 500 个事件，同一天连锁深度最多 64 层，单个事件最多安排 64 个后续事件。
6. **决策。** 决策是带 `decision` 规格的事件。重大决定在 `stopAtMajorDecision` 为真且没有记录选择时暂停，等待 `decide()`；玩家的选择记入快照，作为动作序列的一部分。没有玩家选择时，由人生原则执行器打分（不含随机成分）。每次决定都产生一条 `decision.made` 事实，记录选项、决定者和理由。
7. **死亡终止。** 主角死亡后清空队列，之后的推进不再产生事实；已故角色的事件在处理前作废。
8. **Node 直接运行 TypeScript。** 所有相对导入写明 `.ts` / `.tsx` 扩展名（`allowImportingTsExtensions`），Node 24 通过类型剥离直接运行源码，headless CLI 与基准不需要构建步骤。依赖边界检查会拒绝不带扩展名的相对导入。

## 理由与取舍

- 每个事件深拷贝一次状态：M1 只有一个角色，状态约 12 KB，1,000 局的基准中位数约 1.7 ms/局，远低于 GDD 的 5 秒预算。M3 加入 NPC 后如果拷贝成为瓶颈，再改为按需复制或结构共享，但不放弃原子提交。
- 每个事件都校验全部角色的 schema：成本小、能尽早发现规则缺陷。批量校准（M5）如有需要，可以提供关闭部分校验的开关，但默认保持开启。
- 已处理事件的键集合会随一生增长（约数百个），写入快照用于检测循环。

## 何时重新评估

M3 引入 Tier1/Tier2 NPC 与 Web Worker 时，重新测量状态拷贝与校验的成本；如果需要异步分批，保持「同一序列的 `advanceTo` 调用得到同一结果」这一约束。

## 补充：增量校验（2026-10-21，M3-035，待维护者审查）

触发：M3-010 加入两位 Tier1 父母后，1,000 局基准中位数从 1.81 ms/局升到 4.34 ms/局（事实数只多 3%），CI 上模板覆盖测试超过 5 秒。剖析显示每个事件 49% 的时间在「对全部角色做 schema 校验」，28% 在深拷贝。

调整（只改实现，不改语义）：

- 决定 4 的「角色与账户的 schema 都通过」改为：**只解析本事件新增或与提交前不同的角色与账户**。已提交的状态必然通过过校验（创建时为空；恢复时整份快照经 `SimulationSnapshotSchema` 解析），schema 校验只取决于值本身，因此逐字段相同的对象无需重复解析。复活检查、事实校验与各系统不变量照旧每个事件全量执行。
- `cloneJson` 的正常路径不再为每个节点拼接路径字符串；只在发现非 JSON 值时重新遍历一次，报出与以前相同的路径和错误类型。
- 结果：中位数 2.72 ms/局；黄金指纹、基准工作量指纹（`3f03ad12…`）与全部事实逐字节不变。`engine.test.ts` 用调用计数锁定「未改动的角色不再解析」，防止退回到按角色总数计费。

补充（M3-036）：`relationships` 也纳入提交前校验。关系图有数组级规则（去重、亲子无环），所以只要本事件改动了关系图，就用 `RelationshipsSchema` 整体校验一次；未改动时只做一次结构比较。代价约 0.2 ms/局（每个事件一次比较），换来非法关系在写入它的事件上就被拒绝，而不是等到读档才发现存档无法恢复。

仍未解决：每个事件仍深拷贝整份状态、各系统不变量仍按角色总数运行。M3-011 让父母拥有自己的事件后要重新测量；如果拷贝成为瓶颈，按本 ADR 原计划改为按需复制或结构共享，并保持原子提交。

后续：[ADR-0011](0011-transactional-copy-on-write.md) 把决定 4 的「状态的深拷贝」换成按需复制的事务草稿，原子提交、校验顺序与错误码不变，「没改动」改为按引用判断。各系统不变量仍按角色总数运行。
